# Feature Specification: 身分證資訊擷取系統

**Feature Branch**: `001-id-card-extraction`  
**Created**: 2025-11-01  
**Status**: Draft  
**Input**: User description: "使用LLM(Gemini API)來建立一個身分證資訊擷取系統。使用者透過網頁上傳身分證正面的圖片或PDF，系統擷取各欄位的資訊後自動填入到畫面中"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上傳圖片並擷取基本資訊 (Priority: P1)

使用者開啟網頁應用程式，選擇並上傳一張台灣身分證正面的圖片檔案（JPG/PNG），系統自動辨識並提取姓名、身分證字號、出生日期等基本欄位，顯示在表單中供使用者確認。

**Why this priority**: 這是系統的核心價值 - 自動化資料輸入，減少人工鍵入錯誤。沒有這個功能，系統就沒有存在意義。

**Independent Test**: 可透過上傳一張標準身分證圖片，驗證系統是否正確顯示所有擷取的欄位資料，即為完整的 MVP。

**Acceptance Scenarios**:

1. **Given** 使用者在網頁上看到上傳介面，**When** 使用者選擇一張清晰的身分證正面圖片（JPG 格式）並點擊上傳，**Then** 系統在 10 秒內顯示擷取的姓名、身分證字號、出生日期、性別、發證日期、發證地點等欄位
2. **Given** 系統已擷取並顯示身分證資訊，**When** 使用者檢視表單，**Then** 所有欄位應以可編輯的文字欄位呈現，允許使用者修正辨識錯誤
3. **Given** 使用者上傳檔案，**When** 上傳過程中發生網路延遲，**Then** 系統顯示進度指示器和預估等待時間

---

### User Story 2 - 支援 PDF 格式上傳 (Priority: P2)

使用者可以上傳包含身分證圖片的 PDF 檔案，系統自動從 PDF 第一頁提取圖片並進行辨識，與圖片上傳有相同的擷取結果。

**Why this priority**: 許多掃描設備預設輸出 PDF 格式，支援 PDF 可提升使用便利性，但不影響核心功能。

**Independent Test**: 可透過上傳一張包含身分證圖片的單頁 PDF 檔案，驗證系統是否正確擷取並顯示資訊。

**Acceptance Scenarios**:

1. **Given** 使用者在上傳介面，**When** 使用者選擇一個包含身分證圖片的 PDF 檔案並上傳，**Then** 系統自動從 PDF 提取圖片並顯示擷取的欄位資訊
2. **Given** 使用者上傳多頁 PDF，**When** 系統處理檔案，**Then** 系統僅處理第一頁並提示使用者「已處理第一頁內容」
3. **Given** 使用者上傳純文字 PDF（無圖片），**When** 系統處理檔案，**Then** 系統顯示錯誤訊息「PDF 中未找到圖片，請上傳包含身分證圖片的檔案」

---

### User Story 3 - 批次處理多筆上傳 (Priority: P3)

使用者可以一次選擇多張身分證圖片或多個 PDF 檔案上傳，系統依序處理每個檔案，並在單一頁面中顯示所有擷取結果，允許逐一檢視和編輯。

**Why this priority**: 對需要大量處理身分證資料的場景（如活動報名）很有幫助，但非初期必要功能。

**Independent Test**: 可透過一次上傳 3 張身分證圖片，驗證系統是否依序顯示 3 組擷取結果。

**Acceptance Scenarios**:

1. **Given** 使用者在上傳介面，**When** 使用者一次選擇 5 張身分證圖片並上傳，**Then** 系統顯示處理進度（如「處理中: 2/5」），完成後以清單方式顯示所有擷取結果
2. **Given** 系統顯示批次擷取結果，**When** 使用者點擊任一筆資料，**Then** 系統展開該筆詳細資訊並允許編輯
3. **Given** 批次上傳中有 1 張圖片辨識失敗，**When** 處理完成，**Then** 系統標記失敗項目並顯示其他成功擷取的資料

---

### Edge Cases

- **檔案格式錯誤**：使用者上傳非圖片/非 PDF 檔案（如 .docx、.txt）時，系統應顯示明確錯誤訊息「不支援的檔案格式，請上傳 JPG、PNG 或 PDF」
- **圖片品質不佳**：上傳模糊、光線不足或角度傾斜的身分證圖片時，系統應提示「圖片品質不佳，部分欄位可能無法辨識」並顯示已辨識的部分欄位
- **檔案過大**：使用者上傳超過 10MB 的檔案時，系統應在上傳前就攔截並提示「檔案大小超過限制（最大 10MB）」
- **非台灣身分證**：上傳其他證件（如護照、駕照）或國外身分證時，系統應顯示「無法辨識為台灣身分證，請確認上傳正確的證件」
- **LLM API 錯誤**：當 Gemini API 回應超時或錯誤時，系統應顯示「辨識服務暫時無法使用，請稍後再試」並記錄錯誤日誌
- **並行處理限制**：當多位使用者同時上傳大量檔案導致 API 配額耗盡時，系統應將後續請求加入佇列並顯示「處理佇列中，預估等待時間：X 分鐘」

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須提供網頁介面，包含檔案上傳按鈕和拖放區域
- **FR-002**: 系統必須接受 JPG、PNG 和 PDF 格式的檔案上傳
- **FR-003**: 系統必須限制單一檔案大小不超過 10MB
- **FR-004**: 系統必須從上傳的身分證正面圖片中擷取以下欄位：姓名、身分證字號、出生日期（民國年格式）、性別、發證日期、發證地點
- **FR-005**: 系統必須將擷取的資訊顯示在可編輯的表單欄位中
- **FR-006**: 系統必須在處理過程中顯示載入指示器和狀態訊息
- **FR-007**: 系統必須驗證上傳檔案的格式，拒絕不支援的檔案類型
- **FR-008**: 系統必須處理 PDF 檔案的第一頁作為圖片來源
- **FR-009**: 系統必須提供明確的錯誤訊息，包括檔案格式錯誤、檔案過大、辨識失敗等情境
- **FR-010**: 系統必須記錄所有處理請求的日誌，包括上傳時間、檔案資訊、處理結果、錯誤訊息
- **FR-011**: 使用者必須能夠手動編輯系統自動填入的任何欄位
- **FR-012**: 系統必須在辨識完成後保留原始上傳的圖片供使用者比對（僅於當前對話期間，不永久儲存）

### 資料隱私與安全假設

- 系統假設僅在處理過程中暫存上傳的檔案和擷取結果，不永久儲存個人資料
- 系統假設使用者自行負責上傳檔案的合法性和授權
- 如需符合個資法規範，需額外澄清：是否需要使用者同意書？資料保存期限？

### Key Entities

- **上傳檔案**：使用者上傳的圖片或 PDF 檔案，包含檔案名稱、檔案大小、MIME 類型、上傳時間戳記
- **身分證資訊**：從圖片中擷取的結構化資料，包含姓名、身分證字號、出生日期（民國年月日）、性別（男/女）、發證日期（民國年月日）、發證地點（縣市）
- **處理記錄**：每次上傳處理的日誌，包含請求 ID、上傳時間、處理狀態（成功/失敗）、錯誤訊息（如有）、處理耗時

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者可在 30 秒內完成上傳圖片並看到擷取結果（包含上傳時間 + 辨識時間）
- **SC-002**: 系統對清晰標準的身分證圖片，欄位辨識準確率達 95% 以上（以 100 張測試圖片為基準）
- **SC-003**: 90% 的使用者可在第一次上傳即成功取得可用的擷取結果（無需重新上傳）
- **SC-004**: 系統能處理並行 10 位使用者同時上傳而不發生逾時或錯誤
- **SC-005**: 所有錯誤情境（檔案格式錯誤、檔案過大、辨識失敗）皆提供明確的使用者可理解的錯誤訊息
- **SC-006**: 使用者表單編輯功能可即時反應，無延遲感（小於 100ms 響應時間）
